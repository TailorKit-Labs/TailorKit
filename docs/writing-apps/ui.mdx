An app supplies UI for the [slots](/concepts/slots) in its contract. A view defines what to show in a slot for a particular [context](/concepts/views).

These examples assume your app is configured to use that contract. Generate its bindings after adding or changing capabilities:

```sh
npx tailorkit generate
```

## Write a view

Put view files in `src/slots/<slot>/` with a `.view.tsx` suffix. This view supplies default UI for the `panel` slot:

```tsx title="src/slots/panel/overview.view.tsx"
import "../../tailorkit.gen";
import { defineView } from "tailorkit/client";

const view = defineView({
  slot: "panel",
  view: "/",
  component: Overview,
});

function Overview() {
  return "Member overview";
}

export default view;
```

The folder identifies the slot. An explicit `view` identifies the context and gives `useContext()` its inferred type. Here, `/` makes this a fallback view.

## Use components and tools

Add another view for `/members/detail`. With `Button` and `showToast` exposed in the contract, generated imports let you use them together:

```tsx title="src/slots/panel/member.view.tsx"
import { defineView } from "tailorkit/client";
import { Button, tools } from "../../tailorkit.gen";

const view = defineView({
  slot: "panel",
  view: "/members/detail",
  component: MemberDetails,
});

function MemberDetails() {
  const { member } = view.useContext();

  return (
    <Button
      variant="secondary"
      onClick={() => tools.showToast({ message: "Selected " + member.name })}
    >
      {member.name}
    </Button>
  );
}

export default view;
```

On a member's page, TailorKit selects this view and supplies the member context. Elsewhere, the panel can fall back to the overview. The button's click callback calls a client tool that shows a toast.

## Supply several instances

For a `tile` slot declared with `multiple: true`, return an entry for each dashboard tile:

```tsx title="src/slots/tile/dashboard.view.tsx"
import "../../tailorkit.gen";
import { defineView } from "tailorkit/client";
import { z } from "zod";

const view = defineView({
  slot: "tile",
  view: "/",
  component: Tile,
  instances: {
    dataSchema: z.object({ title: z.string(), value: z.number() }),
    resolve: () => [
      {
        key: "members",
        metadata: { position: { column: 1, row: 1 } },
        data: { title: "Members", value: 12 },
      },
      {
        key: "tasks",
        metadata: { position: { column: 2, row: 1 } },
        data: { title: "Open tasks", value: 8 },
      },
    ],
  },
});

function Tile() {
  const { data } = view.useInstance();
  return data.title + ": " + data.value;
}

export default view;
```

`resolve` runs on the app server. It can use the current context and registered queries to load entries. `useInstance()` reads the selected entry in the UI. The surrounding dashboard decides how to use `position` metadata.

For a repeatable page slot, use the same pattern with keys such as `reports` and `activity`, and metadata such as `{ label: "Reports", icon: "chart" }` for sidebar links.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Does naming a file index.view.tsx make it the default view?">
    It produces `/index`. Set `view: "/"` explicitly for a default view, as the
    overview example does. Only `.view.tsx` files register views.
  </Accordion>
  <Accordion title="Where do instance labels and layout rules belong?">
    Return labels, icons, or placement hints in `metadata`. The surrounding UI
    uses them to build links or arrange tiles. Put values your view needs to
    render in `data`.
  </Accordion>
</AccordionGroup>

## SDK reference

Import `defineView` from `tailorkit/client`. The build discovers `.view.tsx` files and extracts instance resolvers into the server bundle.

The resolver receives `{ context, identity, signal, queries }`. It can call registered queries; actions and mutations are unavailable there. `dataSchema` validates the resolver's data before it reaches the UI.

`slot` must match the enclosing folder; `view` overrides filename-based context discovery. For `multiple: true` slots, `instances` is required. Each entry has a stable, non-empty key unique within the view, metadata, and schema-validated data.

See [ViewInstances](/sdk/interfaces/ViewInstances) for the resolver and [ViewInstance](/sdk/interfaces/ViewInstance) for each entry.
