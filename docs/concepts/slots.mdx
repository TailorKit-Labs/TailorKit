## What is a slot?

A slot is a named place for UI. It might be a side panel, part of a navbar, or a whole page. The green areas below are two slots:

![An app wireframe with a navbar slot and a side panel slot highlighted in green.](/images/slots-wireframe.svg)

## Define slots

Give each area a name in your contract. This defines the two slots in the picture:

<Tabs>

<Tab title="Zod">

```ts title="tailorkit.ts"
import { defineContract } from "tailorkit";
import { z } from "zod";

export const contract = defineContract({
  views: { "/": z.object({}) },
  slots: {
    navbar: { views: ["/"] },
    panel: { views: ["/"] },
  },
});
```

</Tab>

<Tab title="ArkType">

```ts title="tailorkit.ts"
import { defineContract } from "tailorkit";
import { type } from "arktype";

export const contract = defineContract({
  views: { "/": type({}) },
  slots: {
    navbar: { views: ["/"] },
    panel: { views: ["/"] },
  },
});
```

</Tab>

<Tab title="Valibot">

```ts title="tailorkit.ts"
import { defineContract } from "tailorkit";
import * as v from "valibot";

export const contract = defineContract({
  views: { "/": v.object({}) },

  },

```

</Tab>

</Tabs>

<Tip>
  Include `/` in a slot's [views](/concepts/views) so apps can provide default
  UI when no more specific view matches.
</Tip>

## Describe the space

Use `description` to tell app authors and agents where a slot appears:

```ts title="Inside your contract's slots"
panel: {
  views: ["/"],
  description: "Right-hand side panel with independently scrolling content.",
},
page: {
  views: ["/"],
  description: "Main content area beside the host navigation.",
},
```

Agents read descriptions in the generated slot documentation while building apps. Your host controls the actual layout and dimensions.

<Tip>
  Describe the slot’s usable width and height at each breakpoint, including any
  padding or scrolling behavior. For example: “360 px wide on desktop, full
  width below 768 px, with independent scrolling.” This helps agents choose
  layouts that fit the available space.
</Tip>

## Multiple slot variations

By default, a slot has one instance per app, showing one view at a time. Set `multiple: true` when you want separate instances that can appear together.

### Use cases

| Slot | Instances | Metadata could describe |
| --- | --- | --- |
| Dashboard tile | A chart, a task list, and a summary | Each tile's position and size |
| Page | Reports, activity, and settings pages | A label and icon for each page's sidebar link |

One app can supply all of these instances. Each has its own key, metadata, and data. Tiles can appear together; page instances can each have a link and open separately.

```ts title="Inside your contract's slots"
tile: { views: ["/"], multiple: true },
page: { views: ["/"], multiple: true },
```

For example, two page instances could have this metadata:

```json title="Page instances"
[
  {
    "key": "reports",
    "metadata": { "label": "Reports", "icon": "chart" },
    "data": {}
  },
  {
    "key": "activity",
    "metadata": { "label": "Activity", "icon": "clock" },
    "data": {}
  }
]
```

Metadata lets you decide how to arrange tiles or build links. TailorKit doesn't automatically position tiles or create routes from it.

## Context chooses the view

A panel can show an overview on a members list and details when a member is open. The slot selects the closest available [view](/concepts/views) for the current context. That changes the UI inside an instance; `multiple` lets you have more instances.

To supply UI and instances from an app, see [Writing apps → UI](/writing-apps/ui).

## SDK reference

Slots live in `defineContract({ slots })`, keyed by the names you choose.

| Field | Type | Meaning |
| --- | --- | --- |
| `views` | `readonly string[]` | Required. Context paths declared in the contract's `views`. |
| `description` | `string` | Optional. Layout and sizing guidance for app authors and agents. Does not enforce dimensions. |
| `multiple` | `boolean` | Defaults to `false`. Set to `true` to allow independent instances from one app. |

```ts
export type SlotDefinitions<TPath extends string = string> = Record<
  string,
  { views: readonly TPath[]; multiple?: boolean; description?: string }
>;
```

Each repeated instance has a stable, non-empty `key` unique within its view, a `metadata` object, and schema-validated `data`. See [Writing apps → UI](/writing-apps/ui#supply-several-instances) for the implementation.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Do I need multiple instances to change UI between pages?">
    No. Views let one instance change with the current context. Enable
    `multiple` when you need distinct tiles, pages, or other entries from the
    same app.
  </Accordion>
  <Accordion title="Does metadata have a fixed format?">
    It's an object with the fields you agree to use, such as `label`, `icon`, or
    `position`. Your UI decides what those fields mean.
  </Accordion>
</AccordionGroup>
