Apps run in a sandbox, without direct access to your components or the surrounding page. A component schema describes what they can use: its props, events, and children.

Patchsmith generates stand-in components for the sandbox. A local bridge passes UI updates to your real components and sends events back to app code. Updates cross this bridge in the browser without a server round trip.

## Define a component

A button shows a component schema with behavior guidance:

```ts title="patchsmith.ts"
import { defineContract } from "patchsmith";
import { z } from "zod";

export const contract = defineContract({
  components: {
    Button: {
      description:
        "Runs onClick when activated by pointer or keyboard. disabled blocks activation. Children provide the button label.",
      fields: z.object({
        variant: z.enum(["default", "secondary"]).optional(),
        disabled: z.boolean().optional(),
      }),
      callbacks: { onClick: {} },
      children: true,
    },
  },
});
```

| Part | What it does | Button example |
| --- | --- | --- |
| `description` | Explains usage and behavior to app authors and agents | How activation and disabled state work |
| `fields` | Describes data props | `variant="secondary"`, `disabled` |
| `callbacks` | Describes events sent back to app code | `onClick` |
| `children` | Allows text or nested components inside | The button's label |

## Connect the real component

Map the schema's name to your existing button when you create the client:

```tsx title="patchsmith-client.tsx"
import { Button } from "@/components/button";
import { createClient } from "patchsmith/react";
import { contract } from "./patchsmith";

export const patchsmith = createClient({
  contract,
  baseUrl: "http://localhost:3000/api/patchsmith/",
  components: {
    Button: ({ props, children }) => <Button {...props}>{children}</Button>,
  },
});
```

A callback describes an event on a component. For an action such as opening a toast or navigating, expose a [client tool](/concepts/tools#client-tools) instead.

See [Write app UI](/writing-apps/ui) for using these components in an app.

## Built-in icons

The primitives include an `Icon` component backed by Lucide. Expose it alongside the layout primitives:

```ts title="patchsmith.ts"
import { defineContract } from "patchsmith";
import { primitives } from "patchsmith/zod";

export const contract = defineContract({
  components: {
    ...primitives(),
  },
});
```

The same primitives are available from `patchsmith/valibot` and `patchsmith/arktype`. Lucide is the supported library today; apps choose an icon by name.

Spread the matching React primitives into your client. The built-in icon renderer shares its request cache across rendered apps:

```tsx title="patchsmith-client.tsx"
import { createClient, primitives } from "patchsmith/react";
import { contract } from "./patchsmith";

export const tailor = createClient({
  contract,
  baseUrl: "/api/patchsmith/",
  components: {
    ...primitives,
  },
});
```

After regenerating app bindings, apps can use the component:

```tsx
import { Icon } from "./patchsmith.gen";

export function ContinueIcon() {
  return <Icon name="arrow-right" size={16} />;
}
```

| Prop | Type | Default | Meaning |
| --- | --- | --- | --- |
| `name` | `string` | Required | A Lucide name such as `arrow-right`; optional SDK types provide local suggestions. |
| `size` | `number` | `24` | Width and height in pixels, from 1 to 256. |

Generated bindings use `name: string`. The contract accepts string names, and the host loader checks their format and length before fetching. Neither checks a local list of known icons. An app can use a newer icon even when its host, platform, or generated bindings come from an older compatible SDK. Names must be lowercase kebab-case and at most 100 characters; paths, URLs, and arbitrary SVG markup are rejected.

Apps can opt into names provided by their own SDK, independently of the host's SDK:

```tsx
import type { IconName, IconProps, LucideIconName } from "patchsmith";
import { Icon } from "./patchsmith.gen";

const library = "lucide";
const name = "arrow-right" satisfies IconName<typeof library>;
const props = { name, size: 16 } satisfies IconProps<typeof library>;

<Icon {...props} />;

// LucideIconName is also available as a direct library-specific type.
const success: LucideIconName = "circle-check";
<Icon name={success} />;
```

`IconName<"lucide">` and `IconProps<"lucide">` select the local Lucide name suggestions and catch misspellings. Plain `IconProps` accepts string names. A newer catalogue can add names before the SDK types are refreshed; apps may pass those names directly until their SDK adds suggestions. These optional TypeScript checks never become a runtime allowlist. Serialized contracts contain an ordinary string schema, so the platform does not need the icon list or a special icon-name schema.

Icons inherit the surrounding text color, including colors set by primitives. They do not accept children and are decorative, hidden from assistive technology. Give icon-only controls an accessible name on the control itself.

The host fetches individual JSON files from `https://icons.tailorkit.app/lucide/v1/` and renders validated SVG geometry inline. Icon data stays out of SDK and app bundles. Concurrent requests for the same icon are deduplicated, and each renderer caches up to 512 icons. The first load reserves the icon's dimensions until its geometry arrives. Missing catalogue entries and failed requests leave an empty space of the same size; a later mount can retry. Icons load in the browser and are initially empty during server rendering.

The `v1` URL identifies Patchsmith's catalogue and geometry compatibility contract, not Lucide's npm major version. Updates add names while retaining existing names and geometry. Old and new SDKs use the same URLs and do not negotiate npm versions. Breaking geometry or naming changes require a new catalogue compatibility version. This applies to versions that support the Icon component and v1 format; hosts predating this API need an initial upgrade.

Deploy catalogue additions before apps depend on them. An older catalogue may return 404 for a newer name; the host keeps the rest of the UI working and a later mount retries. Successful icons are cached; failed lookups are not permanently cached. Adding an entirely new library still requires a host renderer that supports that library.

The standalone `Icon({ library: "lucide" })` helpers remain available for custom component names and overrides. To self-host, serve the same versioned catalogue directory and override the renderer after spreading the primitives:

```ts
import { Icon, primitives } from "patchsmith/react";

const components = {
  ...primitives,
  Icon: Icon({
    library: "lucide",
    baseUrl: "https://assets.example.com/icons/",
  }),
};
```

The renderer appends `lucide/v1/<name>.json` to this URL and also accepts a `fetch` implementation. Cross-origin catalogues must allow your host origin through CORS. Allow the catalogue origin in your page's `connect-src` policy if you use one. See the dedicated assets project's [catalogue build instructions](https://github.com/patchsmith-io/patchsmith/tree/main/apps/icons-assets) for generating the files and retaining their license notices.

## Change a component schema

Removing a field, an allowed variant such as `"secondary"`, or a callback can break apps that use it. Adding a required field can break them too. Prefer optional additions and keep existing names and values until those apps have migrated.

## SDK reference

Each entry in `defineContract({ components })` describes one component. `Schema` means a Standard Schema validator, such as Zod.

| Field | Type | Meaning |
| --- | --- | --- |
| `description` | `string` | Optional usage and behavior guidance, included in generated component references and binding comments. |
| `fields` | `Schema` | Data props. Field names must differ from callback names. |
| `callbacks` | Callback definitions by name | Function props for events such as `onClick`. |
| `children` | `boolean` | Defaults to `false`. Allows text or nested components inside. |

A callback can declare `input` for its event payload and `output` for its result. Its app implementation can return the result directly or return a promise. `{}` declares no arguments and a `void | Promise<void>` app return type.

Host callbacks always return promises because results cross the sandbox bridge. Await the result in your host component:

```ts
const contract = defineContract({
  components: {
    Editor: {
      callbacks: { onValidate: { output: z.boolean() } },
    },
  },
});

// App implementation; returning Promise<boolean> is also accepted.
const onValidate = () => true;

// Host component:
const valid = await props.onValidate();
```

Callbacks cannot supply an immediate return value to a host API that requires a synchronous result. Callback exceptions and rejected promises reject the host promise. Pending calls reject when the sandbox closes or after 30 seconds without a result.

```ts
export interface CallbackDefinition<
  TInput extends Schema | undefined = Schema | undefined,
  TOutput extends Schema | undefined = Schema | undefined,
> {
  input?: TInput;
  output?: TOutput;
}
```

## Frequently asked questions

Apps can use only the components you expose. Use tools for actions that do not describe component events.

<AccordionGroup>
  <Accordion title="Can an app import any component from my codebase?">
    It uses generated stand-ins for the components you expose in the contract.
    The client mapping keeps the real implementations outside the sandbox.
  </Accordion>
  <Accordion title="Should showing a toast be a component callback?">
    Use a [client tool](/concepts/tools#client-tools) such as `showToast` for
    that action. Callbacks describe events from a rendered component, such as a
    click or selection.
  </Accordion>
</AccordionGroup>
